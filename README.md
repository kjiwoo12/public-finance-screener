# 공공부문 재정 스크리너

지방공기업 427곳의 공개 결산자료를 훑어서 **"이 기관, 이 항목은 물어봐야 한다"** 를 뽑아내는 도구입니다.

판정하지 않습니다. 질문을 만듭니다. 이 구별이 이 저장소의 전부입니다.

---

## 어디에 쓰는 물건인가

**감사 대상을 고르는 데 씁니다.** 무엇이 잘못됐는지 맞히는 도구가 아닙니다.

427곳을 매년 다 감사할 수는 없습니다. 그래서 어디를 볼지 골라야 하는데, 고르고 나면 반드시 따라오는 질문이 있습니다 — **"그럼 저기는 왜 안 봤나."** 민원·언론·전년도 지적사항으로 대상을 정하면 이 질문에 답할 방법이 없습니다. 안 본 곳에 대해서는 아무 기록도 남지 않기 때문입니다.

이 도구는 1,620건을 전수로 훑고 **1,604건을 왜 떨어뜨렸는지 세어서 남깁니다.** 올린 16건보다 이쪽이 요점입니다.

### 그래서 정확도보다 빠뜨림이 중요합니다

| | 대가 |
|---|---|
| 잘못 올림 | 감사인이 결산서 주석을 열어 본다 — 반나절 |
| 안 올림 | 그 기관은 아무도 안 본다 |

1,620건 중 16건이면 사람이 다 확인합니다. **정밀도가 중요해지는 것은 후보가 사람 손을 넘칠 때인데, 이 도구는 넘기지 않습니다.** 반대로 누락은 회복되지 않습니다.

그래서 이 저장소는 **정밀도를 숫자로 내지 않습니다.** 낼 수 없기도 하고(아래에서 다룹니다), 이 용도에서 결정적이지도 않기 때문입니다.

덧붙여 두면, 지금 임계값은 오히려 **좁은 쪽**입니다. 분포의 95분위에서 뽑아 1,620건 중 16건만 남겼습니다. 위 비대칭대로라면 넓힐 여유가 있고, 넓혀야 할 근거가 생기면 넓히는 방향이 맞습니다.

## 왜 판정이 아니라 질문인가

공개된 결산 숫자만으로는 잘못을 단정할 수 없습니다. 부채비율이 300%를 넘는 것은 사실이지만, 그것이 문제인지 아닌지는 그 기관이 무슨 사업을 하는지 봐야 압니다. 대규모 택지개발을 하는 공사는 원래 그렇습니다.

그래서 이 도구가 내놓는 것은 순위표가 아니라 **확인이 필요한 항목의 목록**이고, 항목마다 이 세 가지를 붙입니다.

| 붙이는 것 | 왜 |
|---|---|
| 원본 수치와 계산식 | 지어낸 숫자가 아니라는 걸 보이려고 |
| **정상일 수 있는 이유** | 이걸 안 쓰면 질문이 아니라 고발이 됩니다 |
| 어느 데이터의 몇 년치인지 | 되짚을 수 있어야 하니까 |

실명 기관에 대해 "부정"이라고 쓰지 않습니다. 근거는 공개데이터와 이미 공표된 지적사항으로만 한정합니다.

## 왜 지방공기업인가

**동종비교가 성립하기 때문입니다.**

상수도사업소·도시개발공사·지방의료원은 지자체마다 있습니다. 전국의 같은 업종 기관끼리 나란히 놓으면 "혼자 튀는 곳"이 의미를 갖습니다.

중앙 공공기관은 이게 안 됩니다. 한국전력과 한국콘텐츠진흥원을 같은 표에 놓아도 아무 말도 할 수 없습니다. 게다가 중앙 공공기관(ALIO)은 재무데이터에 오픈API가 없어서 엑셀을 손으로 내려받아야 합니다. 손으로 받은 데이터로 만든 저장소는 남이 다시 돌려볼 수 없습니다.

## 확인된 사실

### 조인 키는 코드가 아니라 기관명 문자열입니다

```xml
<AC_YEAR>2024</AC_YEAR>
<ENT_NAME>안양시공영개발</ENT_NAME>
```

기관코드가 없습니다. 이름으로 이어야 합니다. 다행히 **네 개 재무 데이터셋의 기관명 427개가 완전히 일치**했고, 임금 데이터 175개는 그 부분집합입니다. 테스트로 고정해 뒀습니다 — 나중에 어긋나면 즉시 실패합니다.

### 임금 데이터는 기관의 41%만 있습니다

427곳 중 175곳뿐입니다. "인건비를 다른 계정으로 옮겼는가" 관점은 모집단이 절반 이하로 줄어듭니다. 이건 도구의 한계가 아니라 **공시 제도의 한계**이고, 산출물에 그대로 적을 것입니다.

### 열 이름의 뜻을 검산했습니다

열 이름이 로마자 약어라(`FIN_BU_YU`, `FIN_JAB_SUM`) 뜻을 짐작해야 합니다. 짐작으로 두지 않고 데이터 안에서 맞춰 봤습니다.

```
DEBTRATE = FIN_BU_SUM / FIN_JAB_SUM × 100   →  2,044행 전부 일치
```

부채비율이 부채계÷자본계와 정확히 맞으므로, 이 열들이 제가 읽은 뜻이 맞습니다.

**금액 단위는 백만원입니다.** 서울주택도시개발공사 2024년 부채계가 `20,023,630`으로 나오는데, 이는 약 20조원으로 알려진 실제 규모와 맞습니다.

### 같은 항목이 데이터셋마다 다릅니다

부채규모와 금융부채 두 데이터셋에 모두 총부채가 있는데, **383건이 서로 다릅니다.**

```
경기교통공사 2020   부채규모 FIN_BU_SUM = 65,457
                   금융부채 TOT_BU     = 0
```

한쪽이 0입니다. 어느 쪽이 맞는지 이 데이터만으로는 알 수 없으므로, **한 관점 안에서는 한 데이터셋만 씁니다.** 두 곳에서 끌어와 섞으면 어느 쪽 숫자인지 말할 수 없게 됩니다.

### 원본이 깨끗하지 않습니다

```xml
<T_WYEAR_WMONTH>0년 93개월</T_WYEAR_WMONTH>
```

평균재직기간 7년 9개월을 이렇게 적어 놨습니다. 시도코드에는 `전남광주통합특별시` 와 `전남광주통합특별시1` 이 따로 있습니다.

**수집 단계에서 고치지 않습니다.** 원본 그대로 옮기고, 고치는 일은 분석 단계에서 무엇을 어떻게 고쳤는지 남기면서 합니다. 조용히 다듬으면 원본과 대조할 수 없게 되고, 그 순간 이 저장소의 숫자는 출처 없는 숫자가 됩니다.

### API 를 붙이며 걸린 함정 둘

이걸 적어 두는 이유는, 문서에 없고 오류 메시지가 거짓말을 하기 때문입니다.

**① 서비스 버전과 오퍼레이션 버전이 다릅니다.**

```
openApiFinaDebt3/openXmlFinaDebt2   <- 3 아래에 2
```

규칙이 없습니다. 포털 화면의 엔드포인트를 보고 하나씩 맞춰야 합니다.

**② 필수 파라미터 이름을 서버가 틀리게 알려 줍니다.**

```
보낸 것: (없음)     -> NOTEXISTPARAMETER_ERROR(acYear)
보낸 것: acYear=2024 -> NOTEXISTPARAMETER_ERROR(acYear)   그대로
보낸 것: ac_year=2024 -> resultCode 0, SUCCESS
```

실제 이름은 `ac_year` 입니다. 오류 메시지를 믿으면 영원히 같은 자리에 있게 됩니다.

### 부채가 만기만 갈아탔는가 ([`skills/debt_maturity_shift.md`](skills/debt_maturity_shift.md))

부채 **총액은 그대로인데 고정부채가 유동부채로 넘어온 해**를 찾습니다. 부채비율만 보면 안 보입니다 — 총액이 그대로니 비율도 그대로입니다. 그런데 갚아야 할 시점은 달라져 있습니다.

```
살펴본 연도쌍 1,620건  ->  발견사항 16건, 기각 1,604건

기각 내역
   1426건  비중 증가가 20%p 미만
     77건  유동부채 증가액이 100억원 미만
     76건  직전연도 부채가 0
     24건  당해연도 부채가 0
      1건  총부채가 20% 이상 감소 (상환 국면)
```

**기각을 세어서 남기는 것이 이 저장소의 요점입니다.** 앞선 프로젝트에서는 기준에 안 걸린 건이 조용히 사라졌고, 그래서 산출물만 봐서는 *"검토하지 않았음"* 과 *"검토했으나 해당 없음"* 을 구별할 수 없었습니다. 감사에서 이 둘은 전혀 다른 일입니다.

나오는 모양:

```
광주광역시도시공사 (2022)
  1년 안에 갚아야 할 부채가 2022년에 5,323억원 늘었다. 전체 부채에서
  차지하는 비중은 21.0%에서 66.3%로 올랐고, 총부채는 6,499억원에서
  10,082억원으로 늘었다.

    2021년 유동부채 비중 = 136,507 / 649,903 = 21.0%
    2022년 유동부채 비중 = 668,830 / 1,008,189 = 66.3%
    비중 증가 = 66.3% - 21.0% = 45.3%p
    유동부채 증가액 = 668,830 - 136,507 = 532,323 (백만원) = 5,323억원

  확인이 필요한 것:
    - 만기가 도래한 것인가, 차환에 실패한 것인가. 공시에 만기 구조가
      없어 이 데이터로는 구별할 수 없다.
    - 이 기관의 사업 성격상 단기 차입을 굴리는 것이 통상적인가.
    - 해당 연도에 계정 재분류나 회계기준 변경이 있었는가.
```

**"확인이 필요한 것"이 비어 있는 발견사항은 만들지 않습니다.** 테스트가 막습니다. 못 하는 것을 적지 않으면 질문이 아니라 판정이 되고, 실명 기관에 대해 판정할 근거가 이 데이터에는 없습니다.

임계값(20%p, 100억원)은 이 데이터의 분포에서 뽑았습니다 — 증가폭 중앙값이 0.00%p, 95분위가 24.5%p입니다. 어디서 가져온 기준이 아니라 이 모집단을 보고 정한 값이므로, 모집단이 바뀌면 다시 정해야 합니다.

### 감사원은 이 기관들을 이 기간에 감사하지 않았습니다

감사원 감사결과 2,000건을 받아 세었습니다. 2020년 이후 공개된 752건 중 우리 427개 기관을 **표제로 내건 것은 7건**이고, 그중 6건이 2021년 4월 이전입니다. 우리가 비교하는 회계연도는 2021~2024입니다.

**기관이 겹쳐도 해가 겹치지 않습니다.** 하남도시공사와 안산도시공사는 발견사항에도 들어 있지만, 같은 기관을 다른 해에 본 것이라 맞혔다고 할 수 없습니다.

### 애초에 "정밀도"는 잴 수 없습니다

스크리너가 올린 건에 아무 감사 기록도 없을 때, 가능한 경우는 둘입니다.

| | |
|---|---|
| 문제가 없었다 | 스크리너가 틀렸다 |
| 아무도 안 들여다봤다 | 맞았는지 알 수 없다 |

**공개 자료로는 이 둘이 구별되지 않습니다.** 감사 기록이 없다는 것은 문제가 없었다는 증거가 아니라 감사가 없었다는 증거입니다. 427곳 중 5년간 감사원이 다룬 것이 7곳뿐이라는 사실이 이걸 그대로 보여 줍니다.

그래서 이 저장소는 **정밀도를 숫자로 내지 않습니다.** 낼 수 없는 숫자를 내는 것이 못 내는 것보다 나쁩니다. 테스트가 코드에 그 계산이 들어오는지 감시합니다.

### 대신 경영평가 등급과 맞춰 봤습니다

행정안전부 지방공기업 경영평가 결과입니다. 기관별·연도별 `가~마` 등급이 공개되어 있고, 우리 427곳 중 **425곳이 이름까지 정확히 일치**합니다. 우리 데이터 기간에 이 기관들을 **사람이 들여다보고 남긴 판단** 중 공개된 것이 이것뿐이라서 씁니다.

```
발견사항 16건 중 대조된 것 14건  ->  하위등급(라·마) 0건 (0.0%)
살펴본 1,620건 중 대조된 것 1,042건  ->  하위등급 129건 (12.4%)
```

두 해석이 다 가능합니다.

- **좋은 쪽** — 부채 만기가 당겨지는 것은 경영평가에 안 잡히는 신호다. 등급이 못 보는 것을 본다
- **나쁜 쪽** — 이 관점이 올리는 것은 아무 판단과도 관계가 없다

**이 데이터로는 둘을 구별할 수 없습니다.** 대조된 것이 14건뿐이라, 12.4%를 14번 뽑아 0번 나올 확률이 우연히도 15.7%입니다. 이 수로는 어느 쪽도 말할 수 없습니다.

경영평가는 **그 해 경영 전반**을 봅니다. 우리가 묻는 것은 **부채 만기 하나**입니다. 두 질문이 겹치지 않으므로, 등급이 높은데 우리가 올린 것을 오답이라 부를 수 없습니다.

방향 하나는 그래도 분명합니다. 이 도구가 등급 낮은 기관을 그대로 다시 골랐다면 **만들 이유가 없습니다** — 등급표가 이미 공개되어 있으니까요. 기존 판단과 겹치지 않는 후보를 낸다는 것까지는 확인됐고, 그것이 쓸모 있는 신호인지 잡음인지가 남은 질문입니다.

### 그래서 지금 상태

말할 수 있는 것은 여기까지입니다.

- 1,620건을 빠뜨림 없이 훑었고, 각 건을 왜 떨어뜨렸는지 남겼습니다
- 올린 16건은 원본 수치와 계산식이 붙어 있어 손으로 다시 확인할 수 있습니다
- 올린 16건이 **실제로 확인이 필요한 건인지는 아직 아무도 확인하지 않았습니다**

세 번째는 결함입니다. 다만 **채점표가 없는 것과는 다른 문제**입니다. 대상 선정 도구에 필요한 것은 "올린 것이 다 맞다"는 증명이 아니라 "빠뜨린 것이 없고 안 올린 이유가 남아 있다"는 확인이고, 그건 위 두 줄이 합니다. 세 번째가 묻는 것은 **이 관점 자체가 감사 착안으로 값어치가 있느냐**이고, 그건 채점표를 만들든 안 만들든 사람이 결산서를 열어야 답이 나옵니다. 다음 순서는 [`skills/benchmark.md`](skills/benchmark.md) 끝에 적었습니다.

## 구조

```
collect/
  datasets.py   여섯 API 의 주소와 성질. 추측한 값이 아니라 확인한 값
  client.py     호출 + 재시도. 받은 XML 을 그대로 먼저 저장한다
  normalize.py  XML -> CSV. 값을 고치지 않는다
skills/         검토 관점. 무엇을 왜 보는지, 임계값이 어디서 왔는지
screen/
  data.py       스냅샷을 기관·연도로 찾아 쓴다
  model.py      발견사항과 기각의 모양
  rules/        관점 하나당 파일 하나
benchmark/
  grades.py     경영평가 등급표. 대조할 수 없는 건을 대조된 척하지 않는다
data/
  raw/          받은 XML 원본 26개
  snapshot/     표로 옮긴 CSV 6개 (커밋 대상)
  benchmark/    대조 자료 + 어디서 언제 받았는지
tests/          35개
```

관점을 `skills/` 의 문서와 `screen/rules/` 의 코드로 나눠 둔 이유는, **무엇을 왜 보는지가 어떻게 계산하는지보다 오래 가기 때문**입니다. 임계값은 데이터가 바뀌면 다시 정하지만, "부채 총액이 아니라 만기를 봐야 한다"는 판단은 그대로입니다. 테스트가 둘이 어긋나지 않는지 확인합니다.

`data/snapshot/` 을 커밋하는 이유는, **인증키를 발급받아야 돌려볼 수 있는 저장소는 아무도 돌려보지 않기** 때문입니다. 클론하면 `--check` 로 바로 확인됩니다.

## 확인하는 것

```
python -m unittest discover -s tests
```

수집 11개가 보는 것:

- **옮기다 흘리지 않았는가** — 원본 XML 의 `<item>` 개수와 CSV 행수가 같은가
- **이을 수 있는가** — 기관명이 데이터셋 사이에서 실제로 맞물리는가
- **다시 만들면 같은가** — 같은 원본에서 같은 바이트가 나오는가
- **새지 않는가** — 커밋될 파일에 인증키처럼 보이는 문자열이 없는가

검토 12개가 보는 것:

- **아무것도 조용히 사라지지 않는가** — 살펴본 수 = 발견 + 기각
- **숫자를 지어내지 않았는가** — 근거가 원본 CSV 의 그 줄과 글자까지 같은가
- **못 하는 것을 적었는가** — 발견사항마다 확인이 필요한 항목이 있는가
- **판정하지 않았는가** — 결론 문장에 "부정·위법·혐의" 같은 말이 없는가

대조 12개가 보는 것:

- **연도를 맞게 붙였는가** — `2023(2022)` 는 회계연도 2022다. 밖을 쓰면 전부 한 해씩 밀린다
- **모르는 것을 아는 척 안 하는가** — 평가 대상이 아닌 해가 분모에 들어가면 안 된다
- **주장이 자료와 맞는가** — 문서에 적은 건수와 코드가 세는 건수가 같은가
- **낼 수 없는 숫자를 내지 않는가** — 코드에 정밀도 계산이 들어오면 실패한다

발견사항이 몇 건인지, 대조 결과가 좋은지는 확인하지 않습니다. 그 수는 임계값을 바꾸면 달라지고, 대조 결과는 자료가 정하는 것이라 나빠도 통과해야 합니다. 위 열둘은 바뀌면 안 되는 값입니다.

## 지금 없는 것

- **조서 형식 출력** — 지금은 콘솔 텍스트입니다. 모집단 정의 / 적용 절차 / 제외 사유 / 발견사항으로 나가야 감사인이 쓰던 서식에 그대로 얹힙니다. [audit-signal-agent](https://github.com/kjiwoo12/audit-signal-agent) 의 렌더러를 가져올 예정이고, **다음에 할 일입니다**
- **발견사항 16건의 실물 확인** — 각 기관 결산서 주석에서 유동성 대체 내역을 찾아 만기 도래인지 차환 실패인지 갈라야 합니다. 16건이면 손으로 할 수 있는 양이고, 이 관점이 볼 값어치가 있는지를 채점표보다 빨리 알려 줍니다
- **관점 다섯 개** — 하나만 있습니다. 대상 선정 도구가 한 각도만 보면 그 각도에 안 걸리는 기관은 여전히 아무도 안 봅니다. 연말 집행 쏠림, 계정 갈아타기, 동종기관 대비 이상치, 돈은 늘고 성과는 정체가 남았습니다
- **동종 분류** — 상수도·하수도·도시개발공사를 나누는 코드가 데이터에 없습니다. 기관명으로 추정해야 합니다

## 준비

```
cp .env.example .env      # 그리고 data.go.kr 인증키를 넣습니다
```

data.go.kr 에서 한국지역정보개발원 API 6종을 활용신청(개발계정, 즉시 승인)하면 됩니다. 인증키는 계정에 하나라 여섯 개를 신청해도 `.env` 한 줄로 끝납니다.

이미 받아 둔 데이터만 볼 거라면 인증키 없이 `python -m collect --check` 로 충분합니다.
